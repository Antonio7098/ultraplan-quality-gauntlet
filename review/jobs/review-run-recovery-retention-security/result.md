# Findings — `run-recovery-retention` (security/misuse lens)

## F1. `RestoreBackup` leaves stale `-wal`/`-shm`; stale WAL frames are replayed into the restored image — restore silently fails its purpose — **HIGH / High confidence**

- **Claim:** `RestoreBackup` renames the backup over `run-control.db` without removing or even detecting pre-existing `run-control.db-wal`/`-shm` sidecars (migration.go:347-351). SQLite binds a WAL to no particular database instance; on next open, leftover committed frames from the *pre-crash* database are applied over the restored older image.
- **Observable bad outcome:** Reproduced with the pinned driver (`modernc.org/sqlite v1.57.0`, scratch module in `/tmp/opencode/waltest`): backup taken after row `pre-backup`; crash with an open WAL containing committed row `post-backup-resurrected`; RestoreBackup-style rename over the main file only; reopen yields **both rows** — the post-backup transaction resurrected — and `PRAGMA integrity_check` returns `ok`. The surface's own integrity gate runs *after* WAL recovery (migrateSchema), so it cannot detect this. Restored state ≠ backup content: the exact guarantee `TestBackupRestoreFixture` asserts, defeated silently.
- **Trigger/preconditions:** A `-wal` exists at restore time. That is precisely the recovery scenario this function exists for: SIGKILL, power loss, or panic skip SQLite's clean-close checkpoint-and-delete. "Stop every UltraPlan process" (docs/recovery.md:238-239) does not remove a dead process's sidecar.
- **Evidence:** migration.go:347-351 (rename only); grep confirms no production code removes `-wal`/`-shm` anywhere in `internal/` (only dev script `scripts/reset-opencode-db.sh:131,139`). Test masks the gap: migration_test.go:124 explicitly calls `checkpointWAL(TRUNCATE)` then closes cleanly before restoring.
- **Counter-evidence searched:** runbook wording ("never copy only the database while a WAL writer is active", recovery.md:241) targets manual copying with a live writer, not the shipped offline path with a crashed one; no cleanup in `preparePrivateDatabase`; `enforcePrivateMode` touches only the main file.
- **Adjacent gap (noted, loud-fail):** `validateBackupIntegrity` (migration.go:354-362) checks physical integrity only, never the backup's schema version — restoring a foreign/newer-schema backup bricks the next open with `ErrUnsupportedSchema`. Loud, operator-recoverable; folded here as context.
- **Regression test:** create repo → accept run A → checkpoint+backup → accept run B → simulate crash leaving dirty `-wal` (copy db+wal aside, or leak the fd) → `RestoreBackup` → reopen → assert only A exists. Currently fails.

## F2. Quota gates count unreclaimable sibling files; backups can permanently wedge the workspace and defeat the reserved-headroom contract — **MEDIUM / High confidence**

- **Claim:** `storageBytes` sums *every* regular file whose name starts with `run-control.db` (retention.go:41-54): the DB, `-wal`/`-shm`, `.bak.*` backups, and any stray same-prefix file of arbitrary size. These bytes feed the Accept soft gate (sqlite.go:391-395), Append hard gate (:618-622), Heartbeat hard gate (lifecycle.go:24-28), and Health status. Meanwhile `pruneMigrationBackups` keeps 3 × up to 512 MiB regardless of quota (migration.go:268-291, default hard quota = 512 MiB), pruning runs only on migration opens, and `Compact` can never reduce backup/sidecar bytes.
- **Observable bad outcome:** Migrating a legacy DB near 500 MiB creates a ~500 MiB backup that alone crosses soft (496 MiB) and approaches hard quota: every subsequent `Accept` is refused (retryable forever), heartbeats refuse once total ≥ 512 MiB, so live owners stop renewing and reconciliation marks their exact-live processes `stalled` indefinitely (never terminal — conservative). No in-product escape exists: compaction frees nothing reclaimable, diagnostics show `failed` with no actionable pointer. The documented ladder's purpose — "reserves 16 MiB for heartbeat, cancellation, recovery, and terminal writes" (recovery.md:232-233) — is structurally defeated because reservation arithmetic includes bytes retention cannot reclaim. Same wedge is trivially produced by accident or by any user-scoped process dropping one large file named e.g. `run-control.db.old`: denial of run control without touching the database.
- **Trigger:** large legacy migration (realistic for long-lived workspaces), or any prefixed stray file ≥ ~496 MiB.
- **Controls/counter-evidence:** recovery.md:230-231 says "free space outside the active database" — gestures at manual remediation but never states backups/prefixed files count against the quota; typed retryable errors and Health surfacing limit blast radius but not permanence.
- **Severity/confidence rationale:** medium because read doors work, status is visible, and manual deletion recovers; high confidence on mechanics (all five call sites verified above).
- **Regression test:** seed a `run-control.db.keepme` fixture > soft quota; assert either exclusion from accounting or an explicit diagnostic distinguishing unreclaimable artifacts; plus a test that post-migration usage with max-size backups still permits reserved writes.

## F3. Unbounded config quota overflows `HardQuotaBytes*80/100` to 0 → compaction pressure permanently on → every acceptance silently destroys fresh terminal journals — **MEDIUM / High confidence**

- **Claim:** `workspace_quota_bytes` parses via `strconv.ParseInt(value,10,64)` with validation only `≥ 64 MiB` (config.go:394-398, 498-499); `normalizeRetentionPolicy` re-checks lower bounds only (retention.go:29). For quota > ⌊MaxInt64/80⌋ ≈ 1.15×10¹⁷ (~108 PiB), both pressure expressions wrap: `q*80/100 == 0` (verified numerically: MaxInt64 → threshold `0`). Then sqlite.go:386 is true for any usage → **every** `Accept` invokes `Compact(ctx,64)`; retention.go:109 sets `pressure=true` → `compactCutoff = now` → stage 1 compacts **all** terminal `full` runs immediately, deleting their progress/message/omission history at the moment they finish, instead of after FullHistory/2. Soft/hard gates stay open (softQuota ≈ MaxInt64), so Health reports `ok` throughout.
- **Observable bad outcome:** An operator setting a near-max quota to mean "keep everything" gets the exact opposite: durable per-run histories of freshly finished runs shredded on the next acceptance, with green diagnostics. Silent data destruction driven solely by a parseable config value.
- **Path:** env/yml → config setter → `runControlRetentionPolicy` (app/run_control.go:153-157) → `OpenSQLite` → policy cached → both overflow sites.
- **Counter-evidence searched:** no clamp anywhere between ParseInt and use; yml and env share the same setter; negative values rejected, huge positives accepted.
- **Regression test:** set quota to `math.MaxInt64`; assert `Accept` does not compact a just-terminalized full-history run (or reject quotas > MaxInt64/80 at normalize/config time).

## F4. Stale migration-lock reclaim unlinks by content, not identity — two openers can race into concurrent schema migrations — **LOW / Medium confidence**

- **Claim:** `removeStaleMigrationLock` reads bytes, probes the recorded PID, then `os.Remove(path)` without verifying the file at `path` is still the inode it inspected (migration.go:140-165). Two processes A and B that simultaneously hit EEXIST on the same stale lock both validate it as dead; A removes and recreates a fresh lock; B — already past its probe — unlinks **A's fresh lock** and acquires its own. Both now hold "the" migration lock.
- **Bad outcome:** concurrent first-time migrations: duplicate backups; identical-nanosecond stamp collides on O_EXCL aborting one opener with retryable `CodeUnavailable`; single-migrator invariant broken with no attacker required. Consequences bounded (SQLite immediate-tx serializes DDL), hence LOW.
- **Fix/regression:** fstat-and-compare (`os.SameFile`) between read handle and unlink target, or unlink-by-open-fd; test with two goroutines racing `acquireMigrationLock` against a pre-seeded proven-stale lock.

## F5. Reconciliation evidence rows are silently discarded exactly when they matter most — **LOW / High confidence**

- **Claim:** `_ = r.recordReconciliation(...)` at lifecycle.go:352 and :411 drops insert failures; `report.Decisions` still records the action. The most plausible failure cause is `SQLITE_FULL`/busy (classifyStoreError → CodeQuota/CodeBusy) — i.e., during the quota incidents this surface exists to navigate.
- **Bad outcome:** decisions taken under disk-full leave no durable trace; support export (`ReconciliationEvidence`) shows fewer/no rows while the in-process report claimed them — diverging audit evidence contrary to TRD.md:2296 ("diagnostics must include … last decision evidence"). Recovery.md:215 tells operators to rely on recorded reconciliation outcomes.
- **Regression:** inject a failing exec for `reconciliation_log` (or fill disk); assert the loss is surfaced (report counter/error), not silent.

## F6. Documented retention windows never execute on their own schedule — aging occurs only as a side effect of Accept-pressure — **LOW / High confidence**

- **Claim:** grep-complete caller set of `Compact` is `Accept`'s ≥80% branch alone (sqlite.go:387; verified). Stage 2/3 cutoffs are age-correct, so semantics converge only when pressure arrives. Below 80% of quota, terminal journals persist fully (and tombstones persist past FullHistory+TombstoneHistory) indefinitely — contradicting configuration.md:235-250's documented 168h/720h lifetimes.
- **Bad outcome:** data-lifetime conformance gap (retention promises not kept), plus quota exhaustion arriving later and more abruptly than the documented gradual ladder implies; workspaces with sparse acceptance accumulate decades-old terminal histories at full fidelity.
- **Counter-evidence:** no timer/web/TUI/CLI trigger exists; docs describe retention as unconditional aging. Fix: invoke `Compact` from the existing 10 s reconcile loops or a startup pass; regression: seed an expired tombstone, advance clock, trigger no acceptance, observe deletion.

## Defended / non-issues

- **Lock-file-as-identity forging** (attacker writes a dead PID's identity to get the lock removed): within the documented POSIX-local trust posture; malformed/unprobeable content fails closed to Busy (pid ≤ 0 → `ErrProcessIdentityUnavailable` → stays Busy; verified migration_test.go:86-91).
- **Lstat→open symlink races** at log open/read: require write access to a 0700 dir owned by the same user; no privilege boundary crossed; DB/lock/backup/temp surfaces are O_EXCL-safe.
- **Sanitizer denylist incompleteness** (marker-less secrets through allowed fields like `tool_result`): acknowledged allowlist+denylist design with omission accounting; no concrete trust transition bypassed.
- **Dual clock authority** (`julianday('now')` vs injected clock): single authority per mode; clock-jump behavior test-pinned (lifecycle_test.go:233-259).
- **Envelope-status divergence, export off-by-one newline, redundant discovery in support branch**: cosmetic; excluded per doctrine.
