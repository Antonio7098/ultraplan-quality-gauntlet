# Findings — `durable-operation-spine` (verification/operability lens)

## Finding 1 — HIGH: Runtime-tier trailing omission flush runs on an already-canceled context, misclassifying ordinary cancellations/timeouts as `persistence_degraded`

**Claim.** In `controlledRuntime.StartRun`, the trailing coalesced-progress flush (internal/app/run_control.go:304-315) appends via `appendRunEventWithRetry(runCtx, …)` after `base.StartRun` returns. On any parent cancellation or deadline expiry, `runCtx` is already canceled, so `repository.Append` fails at `BeginTx` and returns `ctx.Err()` verbatim (internal/runcontrol/sqlite.go:639-644). That error poisons `persistenceErr`, which bypasses `terminalOutcome` entirely and proposes `TerminalPersistenceLost` ("durable event persistence failed") for what is actually a clean user cancellation or timeout (run_control.go:322-331), and replaces the returned error with `persist progress omission: context canceled`.

**Observable bad outcome (reproduced).** Ctrl-C / SIGTERM (`signal.NotifyContext`, cmd/ultraplan/main.go:19) or request-deadline expiry during any sprint/study inner run that has one pending coalesced duplicate (two identical progress ticks inside the 250 ms window — the normal steady-state during long stages) yields:
- durable terminal outcome `persistence_degraded`, reason `"durable event persistence failed"` — false storage-outage alarm in the journal, `/runs/<id>` timeline, and health projections;
- user/adapter-facing error `"persist progress omission: context canceled"` blaming persistence for a plain cancellation;
- timeouts recorded as degraded instead of `timed_out`.

Repro: `TestVerifyCancelWithPendingCoalescedProgress` fails with `outcome="persistence_degraded" reason="durable event persistence failed"`; the contrast case without a pending duplicate passes with `cancelled` — isolating the precondition precisely.

**Trigger/preconditions.** Parent ctx canceled or deadline exceeded while `progressOmitted > 0` at base-runtime return. No storage fault required.

**Evidence path.** runCtx := WithCancel(ctx) (:184) → parent cancel cancels runCtx → base returns `context.Canceled` → flush attempt on runCtx (:305) → Append BeginTx fails returning `ctx.Err()` (sqlite.go:641-643) → `persistenceErr` set (:313) → skips `terminalOutcome` (:334) → ProposeTerminal(`TerminalPersistenceLost`) succeeds because fence/run are still active (:322-327).

**Existing controls / counter-evidence searched.** `appendRunEventWithRetry` retries only `ErrUnavailable|ErrBusy`; `context.Canceled` isn't retryable, and the 5 s wall deadline can't help a dead context. The manager tier does NOT have this bug: `durableCLICommand.Finish` (durable_operations.go:78), TUI (tui/app.go:303), and web (web/operations.go:235) all finish on a fresh detached 30 s context — the asymmetry shows detached-flush is the intended discipline and the runtime-tier flush missed it. No test in frozen HEAD covers flush-failure outcome mapping (pack §10 concedes this; grep confirms). TRD L2202/L2223/L2367 require truthful fail-closed/degraded semantics and detectable partial success; this manufactures a degraded verdict where none occurred.

**Severity / confidence.** High / high (minimal repro executed against frozen source `5d54525b`).

**Regression test.** My `TestVerifyCancelWithPendingCoalescedProgress` (sandbox `/tmp/opencode/upgo-verify/internal/app/zz_verify_spine_test.go`) plus a `WithTimeout` variant: emit two identical progress events, cancel parent, assert `TerminalOutcome == TerminalCancelled` (and `timed_out` for deadline), and that the returned error neither claims persistence failure nor drops cancellation identity. Fix shape: perform the trailing flush on a detached ≤30 s context (matching `FinishOperation` discipline) before reading `persistenceErr`.

## Finding 2 — MEDIUM: Manager-tier control-tick failures cancel silently and are durably recorded as user cancellations, with zero diagnostics

**Claim.** `controlOperation` (internal/app/durable_operations.go:223-264) treats any Snapshot/AcknowledgeCancellation/Heartbeat/Reconcile error as `owned.cancel(); return` — no persisted warning/omission event, no log, no surfaced error. The subsequent `FinishOperation` maps the resulting `context.Canceled` to `TerminalCancelled`/"operation cancelled" (:291-292) before any failed-state branch. Unlike the runtime tier, which records `setPersistenceErr` and distinguishes shutdown from real failure via `runCtx.Err()` guards (run_control.go:265, :281, :291) and ends in `persistence_degraded`, the outer tier makes a transient SQLite outage indistinguishable from a user pressing cancel.

**Observable bad outcome (reproduced).** Injected single-shot Snapshot failure: operation context dies within one 1 s tick; journal reads `[lifecycle, terminal]` with outcome `cancelled`, reason `"operation cancelled"` — no warning, no omission, nothing. Operators post-morteming "who cancelled this run?" get the wrong answer; lease-liveness/persistence incidents are invisible in the durable record. Presentation amplifies it: the TUI emit callback swallows `RecordOperationEvent` errors outright (tui/app.go:289-291), so the stream just freezes.

**Trigger/preconditions.** Any single repository error on one owner tick while an outer operation is active (busy-timeout exhaustion under concurrent writers is a realistic source given per-run heartbeats/reconciles).

**Evidence path.** ticker case → `Snapshot` err (:235-239) → `owned.cancel()` → product drains with Canceled → adapter finish → `FinishOperation` maps `errors.Is(runErr, context.Canceled)` first (:291) → `ProposeTerminal(cancelled)` wins; no diagnostic write exists anywhere in the path.

**Existing controls / counter-evidence searched.** LocalFileLogger logs only repository-level events, none generated here since the goroutine exits without calling anything. Cross-manager finishes rely on reconcile, but here the run is actively terminalized by its own owner, so reconciliation never re-classifies it. Existing tests never drive tick paths (pack §10). The in-repo untracked `zz_gauntlet_repro_test.go` (NOT part of frozen HEAD — leftover artifact; its REPRO 1 also hangs because its spy is never canceled) sketches this scenario but pins rather than fails the buggy behavior; I re-derived and confirmed it independently.

**Severity / confidence.** Medium / high (mechanism fully traced; empirical shape confirmed; severity bounded because execution still fails closed safely — the damage is to record truth and diagnosability).

**Regression test.** Fault-injected `Repository.Snapshot` wrapper (as in my `TestVerifyManagerTickFailureIsSilentlyRecordedAsUserCancellation`): assert either a persisted warning/diagnostic event exists before the terminal, or the outcome is `persistence_degraded`; and that a genuine cancellation (no injected fault) still yields `cancelled`. Fix shape: mirror the runtime tier — record the error (warning event + persistence-lost terminal) and add the `ctx.Err()` shutdown guard parity.

## Minor observations (below reporting threshold alone)

- **Hub projection diverges on timeouts:** web `finish()` has no `timed_out` branch — DeadlineExceeded renders as `failed` in SSE/hub state while the durable journal says `timed_out` (web/operations.go:286-294 vs durable_operations.go:289-290). Display-only divergence.
- **`payloadHash` is concatenation, not a hash,** and is ambiguous for keys containing `=` ({"a":"b=c"} ≡ {"a=b":"c"}, run_control.go:730-752); worst case is one distinct progress tick suppressed into the omission count within a 250 ms window. Values are NUL-stripped, so blast radius is tiny.

## Defended non-issues (checked, with disproof)

- **Empty CLI digest breaking repeat accepts:** `Accept` inserts alias rows only when non-empty (sqlite.go:445) and `confirmation_digest` carries no UNIQUE constraint (schema sqlite.go:259) — sequential CLI operations accept cleanly.
- **Retention policy mismatch killing mixed CLI commands:** `runRepository` passes the identical `runControlRetentionPolicy(effective.Config)` as `controlledRuntimeFor` (run_commands.go:54 vs run_control.go:146) — no mismatch path.
- **Silent retention misconfig:** durations/quota validated at config load (config/config.go:487-500); `runControlRetentionPolicy`'s ignored parse errors see only validated strings.
- **Smoke escaping the spine:** `RunSmoke` never touches the runtime interface (no StartRun references in internal/sprint/smoke.go); plain `NewService` in both adapters is consistent.
- **Fingerprint trust boundary:** transport `ExpectedFingerprint` cleared then recomputed server-side (operations.go:215, :367-372), re-verified before dispatch (:401-408); web dedup keys derived server-side from session+token (security.go:448). Holds.
- **QA fence post-terminal:** `ProposeTerminal` sets `attempts.outcome` (sqlite.go:787-788), so post-finish heartbeats correctly fail `StaleFence` — fencing intact.
- **Per-operation reconcile cadence cost:** batched `LIMIT`-bounded scans (lifecycle.go:321-367); healthy-path cost is two indexed queries per active run per 10 s — not a hazard at web caps (8 ops) or study parallelism (≤64).
- **Cross-mutex ordering (inner eventMu → outer eventMu via TUI observer chain):** one-directional; no reverse acquisition exists — no deadlock.
