# Findings: `sprint-smoke-gate` deep review

Reviewed at frozen commit `c6f01cf` (working tree verified byte-identical for all smoke-surface files: `git diff c6f01cf..HEAD -- internal/sprint/` empty except QA files outside this surface). Baseline `go test ./internal/sprint/ ./internal/platform/process/` green in an isolated clone. Behavioral claims below were verified empirically with probe tests at `/tmp/opencode/smoke-probe/internal/sprint/smoke_probe_test.go`.

## F1. A failing diagnostic-only smoke probe erases all durable trace of the failure and leaves the sprint reporting pass

- **Category:** correctness / misleading success · **Severity:** P1 · **Confidence:** confirmed (reproduced)
- **Claim:** When a rerun with `--test` (or any `DiagnosticOnly` scope) executes and fails, the run returns `Status=completed` with no commit, and `saveSmokeAttempt` then writes `status="completed"` into flow-state while keeping the prior complete verdict (`pass`) and recording a clean `LastAttempt{status=completed, diagnostics=[]}`. No product-owned surface records that the probe found a defect.
- **Observable bad outcome:** Sprint 01 passes a full smoke suite, then an operator runs a single-test diagnostic that fails with an open issue. Afterwards: `flow-state.json` shows `status=completed, verdict=pass, runId=<old>`, last attempt completed with zero diagnostics; `sprint validate smoke` reports zero findings; `VerificationStatus` returns `assessment=pass`, smoke fresh; web/TUI/durable operation history all show success. A real product defect surfaced by deep smoke exists nowhere except the CLI process's stdout.
- **Trigger:** Any `DiagnosticOnly` run whose synthesized verdict is `fail` or `pass_with_open_issues`. Preconditions: a prior committed completion (so `LastComplete` exists), non-dry-run.
- **Evidence:** `internal/sprint/smoke.go:177-181` (verdict/status set, early return before `commitSmoke`), `smoke.go:225-228` (restore guarded by `result.Status != SmokeCompleted`, so the pass/fail distinction never reaches state), `smoke.go:234-250` (`smokeAttemptStatus(completed, nil)` = `AttemptCompleted`, no diagnostics since `err == nil`), `smoke.go:31-38` (terminal attempt saved unconditionally).
- **Execution path:** reproduced end-to-end in probe `TestProbeDiagnosticFailureLeavesStalePassState`: baseline pass commit → diagnostic rerun returning `{scope=test, counts={total:1,failed:1}, issues:[ISS-1 open]}` → assertions confirm stale-pass state, clean validation, pass assessment, unchanged `smoke.md`.
- **Existing controls / counter-evidence:** The CLI exits nonzero and renders the fail verdict, so the interactive operator is informed. The design intentionally keeps diagnostic runs from replacing containing-suite evidence (TRD §18.9.2). But writing `status=completed` plus a fresh clean attempt is not a no-op; it selectively keeps the state mutation and drops the outcome.
- **Fix direction:** Record the diagnostic outcome on the attempt (persist `result.Diagnostics`, verdict, and `DiagnosticOnly` fact) or skip the terminal status overwrite entirely for `DiagnosticOnly` results; never let a failing probe upgrade the recorded attempt to clean-completed.
- **Regression test:** Rerun probe scenario asserting `LastAttempt` carries the failure (non-empty diagnostics or a diagnostic-status) and/or that flow-state status is not upgraded to `completed` with the stale verdict.

## F2. The TUI/web `smoke-start` operation can never succeed

- **Category:** correctness / broken entrypoint, TUI parity violation · **Severity:** P1 · **Confidence:** confirmed
- **Claim:** `OperationSmokeStart` builds its service as `NewService(root).WithPublisher(...).WithSmokeSettings(...)` without `WithRuntime` and without `WithStageRuntime`/model resolution, unlike every sibling branch (`OperationVerifyStart` uses `sprintRuntimeService`). Authoring is mandatory on every non-dry run, and the review-freshness re-check needs model resolution, so the operation fails unconditionally.
- **Observable bad outcome:** From the web API or TUI, confirming a smoke start fails every time. With a normally configured workspace (a resolvable review/default model), it fails after preflight at authoring with `smoke_author_runtime`. In configurations where no model resolves, `PrepareReview` yields a "missing review model" finding, the review is marked stale, and the user gets `smoke_review_stale` ("stale reviews cannot be overridden"), which sends them to rerun review even though their review is current.
- **Trigger:** Any `smoke-start` dispatch through `internal/app/operation_runner.go:80` (web handler wiring at `internal/web/operation_handlers.go:682`; operation registered in `internal/app/operations.go:304-310`).
- **Evidence:** `operation_runner.go:79-87` versus `sprint_commands.go:779` (runtime-equipped service); mandatory authoring at `internal/sprint/smoke_author.go:21-23`; gate staleness from PrepareReview findings at `internal/sprint/smoke_protocol.go:185-196`; contract TRD §18.9.3 (~L2077-2079): TUI must expose the same review/smoke behavior as the CLI, and "CLI/TUI agreement" is a required test.
- **Reproduction:** probe `TestProbeWhyWebSmokeStartFails` (bare service shape): `PrepareReview` reports the configuration finding; `TestProbeWebSmokeStartServiceLacksRuntime` shows the resulting gate failure. In production configs the same shape reaches the nil-runtime guard instead.
- **Counter-evidence considered:** Dry-run previews work (authoring skipped), and `verify-start --to smoke` works because it uses the runtime-equipped service. Neither makes the advertised direct smoke-start door functional.
- **Fix direction:** Build this branch through `sprintRuntimeService(deps, root, ...)` like `OperationVerifyStart`.
- **Regression test:** App-level test dispatching `OperationSmokeStart` through the shared runner with fake runtime, asserting completion.

## F3. Manifest environment declarations are inert, and TRD's required "unavailable required environment ⇒ blocked" classification does not exist

- **Category:** contract violation / correctness of gate classification · **Severity:** P2 · **Confidence:** confirmed
- **Claim:** `smokeEnvironment` forwards exactly the configured allowlist (`settings.Environment`), unconditionally. The loop over `manifest.Environment` can never add anything because `names` is initialized to a full copy of the allowlist and candidates must already be members. Separately, nothing in the smoke surface inspects environment availability to produce a `blocked` verdict.
- **Observable bad outcomes:** (a) A harness whose manifest declares a required credential name receives nothing when the operator hasn't added it globally; the run proceeds, and the missing dependency surfaces as arbitrary harness failures or, worse, skipped-path passes, instead of the contracted `blocked` classification with actionable guidance. (b) Conversely, `PATH` and `HOME` are forwarded to every harness child although `docs/configuration.md:230` states "`PATH` and `HOME` are not forwarded by default" and tells operators to add "a manifest-declared name" as if declaration mattered. Three sources disagree: docs, config default (`config.go:189` includes all five), and code.
- **Trigger:** Any smoke run; (a) requires a manifest declaring a name absent from `smoke.environment`.
- **Evidence:** `internal/sprint/smoke_protocol.go:623-642`; `internal/sprint/smoke_test.go:108-128` pins allowlist-only forwarding with an empty manifest; TRD §18.9.2 L2069: "classify unavailable required environment as blocked"; required-test list L2081 includes "blocked environment" (no such test exists); grep confirms no getenv-derived blocked verdict anywhere in `internal/sprint/smoke*.go`.
- **Reproduction:** probe `TestProbeManifestEnvironmentIsInert`: declared-but-unallowed `EXTRA_OK` dropped despite being present in process env; allowed-but-undeclared name forwarded; no manifest value changes the outcome in either direction.
- **Counter-evidence:** The security-critical direction holds (the manifest cannot expand forwarding); the allowlist bounds exposure. That does not satisfy the documented contract for required-environment handling.
- **Fix direction:** Compute effective names as manifest ∩ allowlist (or drop the manifest field explicitly), emit `blocked` with the missing-name list when a declared name is unset or unallowed, and align `DefaultSmokeSettings`/docs on whether `PATH`/`HOME` forward.
- **Regression test:** Manifest declaring a name that is unset ⇒ selection verdict `blocked` naming it; declared-and-set within allowlist ⇒ forwarded; undeclared allowlist name ⇒ not forwarded (or documented otherwise).

## F4. `commitSmoke` discards the input-fingerprint error, then roadmap marking and git publication proceed over a split-brain state

- **Category:** reliability / state consistency · **Severity:** P2 · **Confidence:** high (code path certain; trigger probabilistic)
- **Claim:** `inputFingerprint, _ := refreshEvidenceFingerprint(identityRefs)` (smoke.go:463) swallows read/hash failures. An empty fingerprint makes `validateSmokeStageState` reject `LastComplete` (smoke_types.go:328), so `SaveFlowState` fails after `atomicWriteFile` already replaced `smoke.md` (smoke.go:448 before 477). `RunSmoke` then continues: the roadmap-delivery mark (smoke.go:39-48) and the publication block (49-59) consult only result fields, so the workspace repo publishes the new `smoke.md` alongside the old `flow-state.json`, committing the inconsistency to history. The terminal attempt is meanwhile recorded as cleanly completed (category `reconciliation` is not mapped in `smokeAttemptStatus`).
- **Observable bad outcome:** A pass run ends with an error and reconciliation guidance, `smoke.md` says pass, flow-state still holds the previous record, and git contains the mismatched pair; `sprint validate smoke` reports artifact/state mismatch until a rerun.
- **Trigger:** Any referenced file (manifest, review.md, evidence, issue file) becoming unreadable between response validation and commit. Plausible with two sprints running smoke concurrently against one cataloged harness (leases are per-sprint, locks.go:112-126), where one run's evidence rotation deletes the other's just-validated files.
- **Existing controls:** Failure is loud (typed `smoke_reconciliation`), the previous artifact semantics are documented, and rerun recovers. Not silently corrupt, but the post-commit continuation contradicts the "every later failure reports reconciliation instead of proceeding" reading of the ordering invariant.
- **Fix direction:** Propagate the fingerprint error before writing the artifact (fail closed, preserving the prior `smoke.md`), and gate roadmap/publication on `err == nil`.
- **Regression test:** Fake runner that removes its evidence file after validation (inject via runner hook or fault-injected store) asserting `smoke.md` is preserved, no roadmap mark, no publication.

## F5. Concurrent smoke authoring on a shared harness blames the author agent for another sprint's changes

- **Category:** reliability / misleading failure attribution · **Severity:** P3 · **Confidence:** medium
- **Claim:** The authoring gate fails the whole run when any harness-tree change outside this sprint's manifest allowlist appears between snapshots (smoke_author.go:82-88). Attribution support is compiled out (`freshness_policy.go:14`), and leases are per-sprint, so two sprints smoking the same cataloged harness concurrently interleave snapshots: sprint B's legitimate writes land inside sprint A's after-diff and abort A with `smoke_author_scope` accusing its own agent.
- **Observable bad outcome:** An honest authoring run fails with "smoke author modified a path outside the manifest allowlist: suite/sprint-b_test.go", naming a file its agent never touched.
- **Trigger:** Two sprints' smoke runs overlapping on one harness with differing or disjointly-used authoring paths.
- **Counter-evidence:** Fail-closed on unattributable change is the deliberate trade-off (comment and disabled switch); sequential reruns succeed. Still a concrete false-failure verdict with a wrong stated cause, worth a guard or a scoped message.
- **Fix direction:** Detect lease overlap on the harness (harness-level advisory lock keyed by resolved root) or reword the error to include the possibility of concurrent sibling runs.

## F6. Evidence and issue hashing reads files unbounded

- **Category:** resource safety · **Severity:** P3 · **Confidence:** confirmed (path), medium (impact)
- **Claim:** `validateSmokeRun` stats each evidence item then hashes it with `hashFile` (smoke.go:359-365), which is `os.ReadFile` of the whole file (smoke.go:707-713). There is no size cap, unlike the 64 MiB bound the same package enforces for authoring snapshots (smoke_author.go:371) and target identity (verify.go:433). Paths originate from the harness response.
- **Observable bad outcome:** A buggy or hostile harness returns an evidence item pointing at a multi-GiB log it wrote under its runs root; UltraPlan reads it fully into memory during validation and can OOM or stall the CLI/web process.
- **Fix direction:** Enforce a max evidence size at `os.Stat` before hashing, mirroring the existing bounded-read doctrine.

## F7. Harness-controlled strings reach `smoke.md` unsanitized on two fields

- **Category:** hardening / content integrity of governed artifact · **Severity:** P3 · **Confidence:** medium
- **Claim:** `RenderSmoke` routes nearly every harness-derived string through `printable()` (backtick flattening) and the content validator, but prints `e.Kind`, `e.Path` (smoke.go:526) and `issue.Path` plus surrounding fields (555, 566) raw. Filesystem names may contain newlines on Linux; `Kind` is entirely arbitrary. A harness can inject fabricated lines (fake findings, instructions) into the committed artifact; the forbidden-substring validator does not cover this, while flow-state validation elsewhere treats newlines in comparable fields (override rationale, smoke_types.go:318) as unsafe, so the threat model is internally inconsistent.
- **Consequence limit:** The harness already steers the verdict inputs, so injection adds little power; main risk is misleading humans/agents reading the evidence document.
- **Fix direction:** Route these fields through `printable()`/line-flattening like their neighbors.

## Defended non-issues

- **Non-zero harness exit with valid fail-verdict JSON is accepted.** Deliberate: `classifyProcessSmokeError` is bypassed only when decoding succeeds, and `smoke_process_unexplained` catches exit≠0 with clean counts (smoke.go:408-409). Coherent.
- **Stderr truncation ignored by smoke.** `StderrTruncated` feeds only QA's lane; smoke's protocol stream is stdout, which is truncation-gated before parsing (101, 154). Diagnostics beyond 1 MiB are lost by design.
- **Double `prepareSmokeStatic`.** The pre-publication re-check can flip the gate onto a finished run as a joined error, but order is defined, fail-closed, and post-commit; noise, not corruption.
- **Roadmap-mark vs publication condition asymmetry.** Unreachable in practice: any fail/blocked review forces `DiagnosticOnly`, so the extra review-verdict term never changes behavior.
- **Single heartbeat vs 2h attempt expiry.** Expiry persistence requires the mutation lease, which the live owner holds; mid-run observers get a derived (unpersisted) view only. Transient display effect for >2h runs at most.
- **Containment primitives.** `EvalSymlinks` + `filepath.Rel`-based `inside()` (artifacts.go:77-83) resists prefix tricks; authoring snapshots reject all symlinks; absolute evidence paths and `..` evidence roots fail closed at prepare time.
- **Discovery identity/closure validation, exact executed-set equality, count arithmetic, single-value JSON decoding, atomic write ordering:** each tested and sound; no bypass found.
