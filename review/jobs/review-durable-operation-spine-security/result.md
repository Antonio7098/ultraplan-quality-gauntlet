# Findings — `durable-operation-spine` (security/misuse lens)

## F1. Manager-tier control-loop failure silently cancels healthy work and journals it as a user cancellation — persistence incidents are invisible
**Severity: medium-high · Confidence: high (empirically reproduced)**

**Claim.** In `controlOperation` (internal/app/durable_operations.go:234-261), any single `Snapshot`, `AcknowledgeCancellation`, `Heartbeat`, or `Reconcile` error calls `owned.cancel()` and returns — no warning event, no omission, no log line, no metric, and no `persistence_degraded` classification. The subsequent `FinishOperation` mapping (:288-297) plus the adapters' cancellation-first logic (`durableCLICommand.Finish` :73-74 checks `Context.Err()` first; `failedOperation` maps `context.Canceled` → `OperationCancelled`; web hub `finish` :288-289) commits terminal outcome **`cancelled` / "operation cancelled"**.

**Observable bad outcome.** A transient storage fault (e.g., hard-quota heartbeat rejection at internal/runcontrol/lifecycle.go:24-28, an I/O error, or contention beyond the driver timeout) kills a running operation and the journal records that *the user cancelled it*. Operators debugging "who cancelled my 40-minute execute" find zero diagnostics anywhere (repository logs only success paths; metrics cover append/acceptance/terminal only). This violates the sprint-35 acceptance criterion "**event loss or persistence failure is never silent**" (workspace `projects/ultraplan-go/sprints/35-durable-run-observability/requirements.md` AC) and is internally inconsistent: the inner-runtime tier treats the *identical* poll/heartbeat/reconcile failures as `persistenceErr` → `TerminalPersistenceLost` with a joined surfaced error (run_control.go:263-296, :322-331), while the outer tier — the one users see as *the* operation — hides them.

**Blast-radius amplifier.** The tick loop runs the **global** `Reconcile` sweep every ≥10s. `Reconcile` propagates any non-stale per-row error (`return report, err`, lifecycle.go:343, :395, :402), so one malformed/problematic run row makes every active operation in every attached process self-cancel within 10 s.

**Trigger/preconditions.** One failed tick query per operation; no repetition needed (appends retry ≤5 s on Unavailable/Busy — Snapshot/Heartbeat have no retry at all).

**Execution path.** tick error → `owned.cancel()` → product code drains with `context.Canceled` → adapter finish maps cancelled → `ProposeTerminal(cancelled, "operation cancelled")`.

**Counter-evidence searched.** Fail-closed cancellation itself is contract-sanctioned (TRD L2223) — the defect is silence + misclassification, not the cancel. No test covers any `controlOperation` branch (confirmed; context pack §10 agrees). Reproduced with an overlay test (`go test -overlay … -run TestReviewProbe`): injected `Snapshot` failure → terminal `"cancelled"/"operation cancelled"`, journal contains only `lifecycle=running` + `terminal`, no warning/omission/persistence events.

**Regression test.** Wrap the repository so `Snapshot` fails once after accept; assert either `TerminalPersistenceLost` or a persisted warning diagnostic exists, and that the terminal reason is not "operation cancelled".

## F2. Durable alias dedup ignores lifecycle: identical confirmations can never be re-run from TUI/web until retention expires (~30 d)
**Severity: medium · Confidence: high on behavior, medium on intent**

**Claim.** `AcceptOperation` resolves an alias conflict to whatever run owns it, regardless of lifecycle (durable_operations.go:106-112). Aliases are inserted on accept (internal/runcontrol/sqlite.go:445-454) and **never deleted** anywhere (only retention/compaction touches rows). Both interactive adapters treat `Existing` as final: TUI shows "matching durable operation already exists" with the old lifecycle and starts nothing (internal/tui/app.go:245-250); web returns a document without creating a record or executing (internal/web/operations.go:193-197).

**Observable bad outcome.** Any legitimate re-run whose canonical request and governed inputs are unchanged is permanently refused from TUI/web. Concrete case: Conformance Review finds issues, the developer fixes **target code**, re-runs review — target code is not among `governedOperationInputs` (operations.go:663-686), so canonical+fingerprint are byte-identical → `Existing:true, Lifecycle:"succeeded"`; no new run is created. Same for retrying a failed `execute-start`. Meanwhile the exact same CLI command accepts fresh every time (empty digest, durable_operations.go:55) — cross-adapter inconsistency. Reproduced: after `FinishOperation(succeeded)`, re-accept returns `Existing=true` bound to the finished run (probe B).

**Trigger/preconditions.** Retry/resubmit of an identical confirmed operation through TUI or web after its run reached any terminal state.

**Counter-evidence searched.** Double-submit protection is clearly intended (release checklist "duplicate-start application"; the hub's own dedup map is deliberately short-lived — reaped with `TerminalRetention` 10 min, operations.go:565-575). But the durable alias outlives that by orders of magnitude with no lifecycle gate, TTL, or adapter-level override (only changing inputs/flags escapes). No contract found sanctioning terminal-state dedup; sprint-35 open question 10 explicitly defers "fresh authorization required for … retry" without resolving it. Reported as an availability/workflow defect, not a security hole.

**Regression test.** Accept → finish → re-accept with same digest must start a new run (or the conflict result must be distinguishable/lifecycle-gated); pin whichever semantic is chosen.

## F3. `payloadHash` concatenation is ambiguous; crafted provider payload keys collapse distinct progress events
**Severity: low · Confidence: high mechanism / low practical impact**

**Claim.** `payloadHash` builds `k=v\0`… with no escaping (run_control.go:730-752). Keys may contain `=` (only NUL/CR/LF/length are filtered at :459). Payload `{"x":"a=b"}` and `{"x=a":"b"}` produce identical hashes (probe C), so two *different* runtime progress events within the 250 ms coalescing window (same type/stage/task) coalesce — the second is dropped from the durable journal and SSE fan-out (:220-227). Attacker-influenced model/provider output can suppress its own observability trail; bounded to progress-type events and a 250 ms window. Fix: escape/hash with a collision-free encoding (the function name promises a hash).

## Defended / non-issues (actively checked)

- **Fingerprint authority holds.** Transport-supplied `ExpectedFingerprint` is stripped and recomputed server-side in both `PrepareOperation` (operations.go:215) and `RunOperation` (:401-410, re-verified before runner dispatch → TOCTOU closed); symlink rejection at :711-721; web tokens are consume-once and bound to session+canonical+fingerprint (operation_handlers.go:151-157); TUI staleness is caught by the same `RunOperation` re-verification even though acceptance precedes it (costs one wasted accepted row, fail-closed).
- **Persisted digests are always server-derived** (sha256 hex) in TUI/web; CLI persists none by design; storage validates alias/digest bounds (sqlite.go:402, :446).
- **RecordOperationEvent's unsanitized-looking fields do not create a leak or cancel cascade:** the storage gate inside `Append` (sqlite.go:617 → sanitize.go) allowlists keys, rejects sensitive keys/values (incl. `\n`, absolute paths, bearer/sk-/ghp_ markers), and converts violations into explicit omissions rather than errors — verified against the app-layer pipeline in run_control.go.
- **SSE projection raw tool fields** (operations.go:265) are pre-redacted/bounded upstream (`redactObservableValue`/`boundedPayloadValue`) and size-capped by `appendEventLocked`.
- **QA writer-token handoff is correctly paired** in all three adapters (token minted from the accepted context; whole-struct equality fence; `WithoutCancel` heartbeat bounded to 30 s; fence installed before `RunQA` at sprint_commands.go:430-441, operation_runner.go:115-123); post-terminal heartbeats fail fenced (stale-fence) — correct fail-closed.
- **Metadata injection cannot be spoofed:** `cloneRuntimeMetadata` copies first and `run_control_run_id` is overwritten server-side (run_control.go:186-187).
- **Cross-session durable status/cancel-by-ID** lacks session binding but rests on 128-bit crypto-random IDs plus HMAC-signed sessions/CSRF — consistent with the documented workspace-local trust posture (capability-style access).
- **Accept-before-execute, commit-before-delivery, no-start-on-persistence-failure** are real and test-pinned (run_control_test.go:49-129); inventory pinning enforces the CLI chokepoint structurally.
