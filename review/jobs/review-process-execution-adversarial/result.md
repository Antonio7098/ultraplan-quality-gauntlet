# Findings — `process-execution` adversarial review

## F1. Shipped documentation contradicts the implemented child-env policy: PATH and HOME *are* forwarded to smoke harnesses

- **Claim:** `docs/configuration.md:230` states "The built-in platform set is limited to `TMPDIR`, `LANG`, and `LC_ALL`; `PATH` and `HOME` are not forwarded by default." The implementation forwards PATH and HOME by default.
- **Observable bad outcome:** An operator or security reviewer configuring/auditing a smoke harness believes an external reviewed harness cannot resolve host binaries via the operator's PATH and cannot observe the operator's home directory. In reality the harness child receives `PATH=<operator PATH>` and `HOME=<operator home>` (path disclosure, and host-binary resolution exactly what the doc claims is prevented). Audit conclusions based on the doc are wrong.
- **Trigger:** Any smoke run with default config (`ultraplan sprint smoke … --yes`, durable-operation door, TUI).
- **Evidence:** `internal/platform/process` consumers build env via `smokeEnvironment` (`internal/sprint/smoke_protocol.go:623-642`) from `settings.Environment`; defaults include both names: `internal/sprint/smoke_types.go:55` (`Environment: []string{"PATH", "HOME", "TMPDIR", "LANG", "LC_ALL"}`) and `internal/platform/config/config.go:189` (identical); the behavior is pinned by `TestDefaultSmokeEnvironmentPreservesInterpreterPath` (`internal/sprint/smoke_test.go:108-127`, explicitly asserts `HOME=/home/smoke` forwarding).
- **Path:** config defaults → `app.smokeSettings` (`internal/app/sprint_commands.go:898-906`) → `smokeEnvironment` intersection → `pprocess.Request.Env` → `cmd.Env` (`internal/platform/process/process.go:86`).
- **Counter-evidence searched:** No other doc section states PATH/HOME are forwarded; the canonical seam record itself says the intersection includes PATH/HOME, so two internal contracts disagree, and code+tests agree against the docs. Not a stale-seam issue — it is a REALITY vs CURRENT-CONTRACT divergence.
- **Severity:** medium (security posture misstatement in shipped docs). **Confidence:** high.
- **Verification/regression:** Doc fix or policy change; a test asserting `smokeEnvironment` output matches the documented built-in set would have failed before either side was corrected.

## F2. Durable-operation (web/TUI) door enforces no cap on request-sourced run timeout, and silently discards malformed timeouts — CLI doors enforce both

- **Claim:** The seam contract says smoke timeouts are capped at 24 h. CLI parsing enforces `--timeout … > 24h` rejection (`internal/app/sprint_commands.go:929-933` and the verify door at `:1236-1240`). The durable-operation door parses `req.Timeout` with the error discarded and no ceiling (`internal/app/operation_runner.go:81-84` for smoke, `:102-105` for verify), and `smokeTimeout` returns request-sourced durations uncapped (`internal/sprint/smoke_protocol.go:644-647`); `DirectRunner.Run` accepts any positive timeout (`process.go:71-73`).
- **Observable bad outcome:** (a) A dashboard/TUI client passing e.g. `"87600h"` as the timeout produces a smoke run whose effective timeout is ten years: the harness may hold the sprint mutation lease and the persisted `running` attempt record indefinitely, blocking all subsequent mutation-stage operations for that sprint with no upper bound. (b) A malformed value (`"30 min"`) is silently converted to 0 and falls through to manifest/settings precedence with zero diagnostics — the operator's explicit bound is dropped invisibly, whereas the identical mistake on the CLI exits with usage error.
- **Trigger:** Any smoke/verify start through `OperationSmokeStart`/`OperationVerifyStart`/TUI with a large or malformed `Timeout` string.
- **Evidence:** cited above; `Result.EffectiveTimeout`/`TimeoutSource="request"` would show the uncapped value in the smoke summary.
- **Counter-evidence searched:** No downstream clamp exists between the operation runner and `DirectRunner` (checked `RunSmoke`, `runSmoke`, `smokeTimeout`, `Request` validation); the 24 h caps found apply only to manifest defaults and CLI flags.
- **Severity:** medium (unbounded resource/lease holding through a documented-capped seam; silent intent loss). **Confidence:** high.
- **Verification/regression:** Unit test running the OperationSmokeStart handler with `Timeout:"999999h"` expecting validation error, and with a malformed value expecting an error (or at minimum a surfaced diagnostic), mirroring `parseSprintSmokeArgs`.

## F3. Harness root resolves relative catalog paths against the ultraplan process CWD; the absolute-path rule lives only in advisory validation that smoke never consults

- **Claim:** For Target Implementation Directory, a relative catalog path is deliberately resolved against the workspace root (`ResolveExecuteTarget`, `internal/sprint/execute_target.go:35-40`). For the Smoke Harnesses row, `prepareSmokeStatic` calls `canonicalDirectory(entry.Path)` directly (`internal/sprint/smoke_protocol.go:130`); `filepath.EvalSymlinks` on a relative path resolves against the process CWD. The "harness path must be absolute" rule exists only in `validateSmokeHarnessEntry` (`internal/project/validation.go:168-171`), which is reachable solely via `project status`/`project validate`; `resolveSprintInputs` gates only on parse findings (`internal/sprint/service.go:988-991`), and `entryFromRow` requires nothing about absoluteness (`internal/project/index.go:60-93`). Manifest, executable, cwd, and evidence containment are then all resolved *inside that CWD-derived root* (`smoke_protocol.go:134-176`).
- **Observable bad outcome:** The same catalog entry executes different harness trees depending on the directory the CLI was invoked from. Demonstrated: with identical relative catalog content, resolving `root` from two directories selects two different roots/executables (`/tmp/opencode/cwd-demo`: invocation from `a/` vs `b/` each selected its own local tree). Concretely: author writes Path=`smoke/harness` intending `/workspace/smoke/harness`; an operator who happens to have an unrelated `./smoke/harness` tree (e.g., a stale checkout) runs smoke from `$HOME` — ultraplan executes that tree's manifest/executable under a fully "valid" containment chain and review gate. When nothing exists at the CWD-relative location, the failure message ("Restore the cataloged harness directory") misdirects instead of naming the missing absolute-path requirement.
- **Trigger:** Relative `Path` in the single Smoke Harnesses row (parse-clean, so it flows straight into smoke/QA status/run).
- **Existing controls:** EvalSymlinks containment still holds within whichever root was selected; review gate is unaffected (it governs product code, not harness identity). Neither control prevents wrong-tree selection.
- **Severity:** medium-low (wrong-binary selection across invocation contexts; reproducibility of the review→smoke chain broken). **Confidence:** high.
- **Verification/regression:** Sprint-level test with a relative harness catalog row asserting smoke refuses it (or resolves it against the workspace root like targets); currently no test pins this (`smoke_test.go` has no relative-root case).

## F4. QA attempts that fail after terminal investigator output are dropped from retained history — including executed-check digests and target-drift events

- **Claim:** In `runOneQAShard` (`internal/sprint/qa.go:726-870`), every in-loop failure appends `attempt` to `shard.Attempts` (:760-789). After the retry loop accepts terminal output, all failure returns omit the append: budget violation :808-809, context-request violations :813-824, catalog rebuild error :826-828, unowned check :834-837, check execution failure :839-843 (this includes `RunApprovedQACheck` returning `QAErrorPermissionDenied` "target identity changed during the approved check" and `QAErrorRuntimeUnavailable` after gofmt actually ran), theory identity/validation failures :845-859, governed-input revalidation :861-862. Only the success path appends (:865). `runQAShardBatch` publishes the returned shard verbatim (:693-700); nothing reconstructs the attempt.
- **Observable bad outcome:** A shard where an approved `gofmt` subprocess really executed (and possibly detected target-tree drift — a security-relevant event) leaves no persisted record of: command summaries/digests, identity before/after hashes, investigator usage/cost, or stop reason. For a product whose doctrine is digest-only audit retention ("attempt history", `RetainedAttempts`), operators inspecting `verification/state.json` see only a blocker string and cannot audit what ran or what drifted. Cost telemetry for that investigator run is also lost.
- **Trigger:** Any investigator output that passes decode but fails downstream validation/checks — most commonly a failing approved check or a drift detection.
- **Counter-evidence searched:** No deferred append in `runOneQAShardSafely` (:716-724 handles panics only); no synthetic-attempt backfill in `runQAShardBatch`; resume reloads only terminal-phase shards (:579-601), so the lost attempt is never recovered.
- **Severity:** low-medium (audit/evidence loss; verdicts remain fail-closed). **Confidence:** high.
- **Verification/regression:** Test driving `runOneQAShard` with a fake runner whose `RunApprovedQACheck` fails (e.g., fake drift) and asserting the published shard contains an attempt with `len(Commands)>0` and the drift stop reason; fails today.

## F5. Discovery validation accepts duplicate identities inside mapping/level/suite lists, deferring failure to a post-execution evidence mismatch with misleading guidance

- **Claim:** `validateSmokeDiscovery` checks only cross-collection existence/ownership: level→suite (:295-304), suite→test plus ownership (:309-323), mapping→suite (:333-337). Duplicates *within* one list pass (e.g., a complete mapping listing suite `"s1"` twice, or `suite.Tests` containing the same ID twice). Downstream, `selectSmoke` preserves duplicates in scope IDs (`smoke_protocol.go:525-526`) and `expectedSmokeTests` concatenates suite test lists without dedup (`smoke.go:414-437`), so expected identities contain duplicates while the harness's actual executed set naturally lists each test once — `smoke.go:342` then rejects the run with "executed test identities/statuses do not match discovery and counts".
- **Observable bad outcome:** A statically detectable discovery defect survives validation, costs a full harness execution (up to the effective run timeout), and then fails with guidance directing the harness author to fix runtime behavior ("Run exactly the selected discovered tests…") when the real cause is the accepted malformed manifest payload.
- **Trigger:** Harness-authored discovery JSON with repeated IDs in `sprintMappings[].suites` / `suites[].tests` / `levels[].suites`.
- **Counter-evidence searched:** No dedup anywhere in the path (`smokeCoverageMapping` dedups only its internal test collection via map, `out.Suites` keeps duplicates); no test covers intra-list duplicates. Fail direction is closed (no wrong verdict), hence low severity.
- **Severity:** low. **Confidence:** high.
- **Verification/regression:** Add duplicate-suite-in-mapping and duplicate-test-in-suite cases to the discovery rejection matrix (`smoke_test.go:213` area) asserting rejection at `validateSmokeDiscovery`.

## Defended hypotheses and non-issues (verified, not reported)

- **Pipe-drain hang after timeout:** Hypothesized `drains.Wait()` hangs forever when an escaped descendant holds the stdout write end (Linux `close()` doesn't interrupt blocked reads). **Disproven empirically** (/tmp/opencode/drain-hang): with `setsid sleep 45 &` escaping the owned group (confirmed surviving with new pgid/session), `Run` still returned exactly at the 2 s timeout — `cmd.Wait()` closes the poller-registered read end, unblocking the drain goroutines. 
- **Escaped descendants leak while `CleanupComplete=true`:** Real (verified above) but the flag's coded invariant is group-scoped and honest; verdicts stay fail-closed (timeout classification). Inherent limit of process-group containment; noted as the pack's known unknown, no misreported state.
- **`RunApprovedQACheck` cwd check tautology:** `validateQACheckDescriptor(descriptor.WorkingDirectory, …)` compares the descriptor to itself, but the invariant is enforced transitively: fingerprint binds `WorkingDirectory`, must equal a map-owned ref built via `ApprovedQAChecks(manifest.Target,…)` (`qa_map.go:106`), and the executor rebuilds the catalog from the same frozen target (`qa.go:826`). Fail-closed.
- **Fingerprint order-dependence:** `ApprovedQAChecks` arg order follows input order, but production inputs pass through `normalizeQAStrings`, which sorts+dedups (`qa_types.go:805-817`); the order-independence test's single `.go` fixture doesn't exercise it, yet production determinism holds.
- **Dead output-budget check:** `OutputBytes > OutputLimit*2` (`qa_prompt.go:281`) is unreachable given per-stream caps equal `OutputLimit`; the `Truncated` clause carries the guarantee. Defense-in-depth, not a defect.
- **`targetIdentity` ignores git-ignored files:** true, but exploiting it requires a malicious *approved* executable; the catalog is product-pinned to `gofmt -d`.
- **`PrepareReview` inside read-only `SmokeStatus`:** inspected — builds manifests/findings from files, no writes.
- **Env values with NUL:** rejected by `exec` at Start → classified as process failure; fail-closed.
- **`WithProcessRunner`:** confirmed test-only injection seam; production default is `DirectRunner{}` (`service.go:76`).
