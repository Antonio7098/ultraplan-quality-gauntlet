## F1. `run list` ordering/pagination compares RFC3339Nano timestamps as strings — temporal order inversions (Severity: medium, Confidence: high)

- **Claim**: `updated_at` is stored via `formatTime` = `RFC3339Nano`, which strips trailing fractional zeros, producing variable-length TEXT (`sqlite.go:1049`). `List` sorts and paginates with raw BINARY string comparison (`lifecycle.go:233` `ORDER BY updated_at DESC, run_id DESC`; keyset predicate `lifecycle.go:230`). String order diverges from temporal order whenever one fraction is a lexical prefix of another or one timestamp is an exact second.
- **Observable bad outcome**: temporally older runs are listed above newer runs — violating cli-reference.md:514 "`list` is newest-first" and the surface invariant "List order is deterministic". JSON consumers inherit the same wrong order.
- **Trigger**: two runs updated within the same wall-clock second with prefix-related fractions (e.g. `.5Z` vs `.51Z`: `'Z'`=0x5A > `'1'`=0x31), or any exact-second timestamp vs any fractional one (`…00Z` sorts above `…00.1Z`). Measured inversion rate among distinct same-second pairs: ~0% on nanosecond clocks, 0.0015% microsecond, **0.55% on millisecond-resolution clocks** (coarse-clock VMs/containers); whole-second stamps are deterministically inverted. All processes sharing a workspace write this column (heartbeat rewrites it every 5s, lifecycle.go:48), so cross-process mixed clock resolutions compound exposure.
- **Evidence**: `sqlite.go:1049`; `lifecycle.go:225-233,255`. Proven end-to-end with injected-clock repro tests through real `Accept`+`List` on modernc SQLite: prefix-pair case returned the accepted-first (older) run at position 0; whole-second case ranked the exact-second run above one updated 100 ms later. Both fail assertions today; they double as regression tests (assert temporal order; currently red).
- **Counter-evidence / limits**: pagination is self-consistent — cursor round-trips the raw string and the predicate uses identical string semantics, so pages tile without dup/skip; the defect is presentation order, not data loss. Existing tests never catch it (fixed clocks at whole seconds or single timestamps). Mutable sort keys additionally allow cross-page churn for active runs (inherent, undocumented — noted, not charged).
- **Fix direction**: fixed-width timestamps (e.g. always-9-digit fraction) or integer epoch-nanos column/comparison; note migration hazard: comparisons across pre/post-format rows would invert worse if formats are mixed within existing DBs.
- **Related observation (run-journal-fencing scope)**: `retentionCandidates` (`retention.go:163`) compares `finished_at <= formatTime(cutoff)` as strings — same class; sub-second skew on day-scale windows makes impact negligible there.

## F2. CLI `follow` silently begins partial streams — missing TRD-mandated typed retention-gap handling (Severity: medium, Confidence: high)

- **Claim**: TRD.md:1255 (current Sprint 35 contract): "an unavailable cursor produces a typed retention-gap result plus the current durable run snapshot rather than silently beginning a partial stream." The web door implements exactly this — `cursor_ahead` conflict when `after > LastSequence`, `replay_gap` when `after+1 < OldestRetainedSequence`, plus oldest-bound clamping on initial follow (`internal/web/run_handlers.go:968-979,337-338`). CLI `run follow` (`run_commands.go:131-195`) implements none of it.
- **Observable bad outcomes**: (a) following a compacted/tombstoned run replays only retained events with zero indication history was dropped (text mode prints no snapshot fields at all); (b) `--after` beyond `LastSequence` on an active run polls forever at 1 Hz printing nothing; (c) same on a terminal run exits 0 with empty output — three distinct "unavailable cursor" conditions, all silent.
- **Trigger**: any operator or automation using `run follow` on a run whose journal was compacted (per-run caps 4096 events/16 MiB, `retention.go:58-95`) or supplying an out-of-range sequence.
- **Execution path**: `Events` returns whatever rows exist above `after` regardless of `oldest_retained_sequence` (`sqlite.go:809-854`); loop exits only on terminal-and-drained (`run_commands.go:180`); nothing compares `after` to snapshot replay boundaries.
- **Counter-evidence**: cli-reference.md:512-520 doesn't promise gap detection for CLI, but TRD is authoritative current planning context and §18C's required failure matrix explicitly includes "cursor expiry"; the sibling surface's implementation confirms product interpretation. I also checked whether the loop can hang on terminal runs generally: it cannot — the terminal event occupies `last_sequence`, so drained terminal runs always terminate; only out-of-range cursors misbehave.
- **Regression test**: compacted fixture + `--after 0` must produce a gap signal (or documented equivalent) instead of a bare partial stream; `--after > last` must not stream silently.

## F3. Interrupting `run follow` during an in-flight store call exits 6 with runtime-failure text, contradicting "interrupting follow stops observation only" (Severity: low-medium, Confidence: high mechanism)

- **Claim/paths**: interrupt during the idle select → clean exit 0 (`run_commands.go:188-192`). But SIGINT landing while `Events`/`Snapshot` is executing surfaces `context.Canceled`, which `classifyStoreError` deliberately passes through unwrapped (`sqlite.go:1103-1104`) and `mapRunControlError`'s default arm wraps as `ExitRuntime` (`run_commands.go:403-414`) — stderr error + exit code 6 ("runtime/store failure" class per cli-reference.md:18-30), for a pure observation stop that user-guide.md:388-389 and cli-reference.md:517 document as harmless.
- **Trigger**: signal timing race; normally a ms-wide window per 1 s cycle, but store calls can block up to `busy_timeout` 5 s under DB contention, widening it materially. No test covers non-terminal follow or ctx cancellation.
- **Bad outcome**: misleading failure classification of a normal operator action; scripts treating exit≠0 as follow failure will alert spuriously.
- **Counter-evidence**: none — grep confirms no handler remaps ctx errors for this path. **Verification**: drive `follow` against an active run and cancel ctx during the Events call; expect exit 0 today only by luck of timing.
