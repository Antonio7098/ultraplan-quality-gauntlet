# Review Report: `run-journal-fencing` (security/misuse lens)

Baseline: `go build`, `go vet`, `go test ./internal/runcontrol/` green at HEAD (runcontrol identical to frozen `5d54525`). Two findings survived counter-evidence hunting; both empirically probed without modifying the target (Go test overlays mapped from `/tmp/opencode`).

## Finding 1 — HIGH severity / HIGH confidence: Backward wall-clock step poisons durable rows via unvalidated Heartbeat commit, then bricks observation, arbitration, and startup reconciliation until the clock re-passes `accepted_at`

**Claim.** Every writer stamps `updated_at = formatTime(r.now())` unguarded (9 sites: sqlite.go:437, 563–565, 678–680, 771–776; lifecycle.go:48, 111–114, 172–175, 456–460, 498–501), while `Snapshot.Validate` strictly rejects `UpdatedAt.Before(AcceptedAt)` (model.go:346–348). A backward wall-clock step (NTP step mode, systemd-timesyncd default on step-worthy drift, VM suspend/resume restore, host migration) between a run's acceptance and any later write makes that row permanently invalid **for every reader and validated writer** until wall time re-passes that run's immutable `accepted_at`.

**The amplifier.** Validation discipline is inconsistent across writers: `Accept`/`Claim`/`Append`/`ProposeTerminal` validate post-write snapshots and roll back; **`Heartbeat` does not validate at all** (lifecycle.go:56–62 — loads snapshot only to discard it) and neither do `RequestCancellation` (:87–96), `AcknowledgeCancellation` (:152–161), or `reconcileUnclaimed` (:436–445). So the heartbeat path *commits* timestamp inversion and reports success to the owner, which is precisely the write an active owner performs every 5 s. `markStalled` also commits poison (no load).

**Observable bad outcomes (empirically demonstrated with injected clock, T1 = accepted_at):**
1. Heartbeat after step-back below `T1`: returns `err=<nil>`, liveness=live — owner believes it is healthy while the row is poisoned.
2. `Snapshot` and `List` fail with `invalid_argument: snapshot.timestamps must start at acceptance and move forward`. Because `List` fully loads every row (lifecycle.go:258–264), **one poisoned row fails the entire page**: `run list/show/follow` and any snapshot-polling consumer are dead workspace-wide for those rows.
3. Owner terminal proposal rejected: `won=false, err=invalid_argument` — non-retryable by app policy (`retryableRunControlError` admits only `ErrUnavailable|ErrBusy`, app/run_control.go:370–372), so the operation's real outcome (succeeded/failed/cancelled) is **never durably arbitrated**; TRD §18C's "one immutable arbitrated terminal result" is lost for the window.
4. With the owner dead past lease+grace, startup-style `Reconcile` selects the candidate and aborts: `report={Scanned:1 Terminal:0}, err=invalid_argument`. First process open runs Reconcile fail-closed (app/run_control.go:66–70) → **every subsequent ultraplan invocation against the workspace errors out** — total lockout for the remaining poisoned window (for a run accepted hours ago, even a 2-minute clock step poisons for hours).
5. Unclaimed poisoned runs are worse: `reconcileUnclaimed` has no validation, so it *commits* an interrupted terminal onto the already-invalid row — permanently unreadable, silently.

**Trigger/preconditions.** Wall clock steps backward across any run's `accepted_at` between that run's accept and a later write; then any read, append, claim, cancel-ack, terminal proposal, or owner-death reconciliation touching it. No attacker required — environment-hostility of the time source is enough; conversely nothing limits it to accidental causes.

**Existing controls / counter-evidence searched.** No clamp anywhere (`updated_at` never takes `max(now, stored)`); no tolerance in Validate; schema CHECKs don't cover timestamps; `TestReconcileClockJumpNeverExpiresAnOwnerEarly` covers lease-expiry direction only — no test exercises timestamp inversion between writes (blind spot confirmed). Atomicity holds throughout (poisoned writes either roll back or commit consistently), so this is availability/arbitration loss, not journal corruption beyond the timestamp pair.

**Regression test.** In-package test with `mutableClock`: accept → advance 2 s → append → rewind below `accepted_at` → heartbeat must not commit inversion (or writes must clamp) → forward past lease+grace still below `accepted_at` → `ProposeTerminal` must succeed or degrade typed-retryable, `Reconcile` must complete, `List` must not abort. Currently fails exactly as documented above (probe preserved at `/tmp/opencode/f1probe/zz_f1_probe_test.go`).
**Fix direction:** stamp `updated_at = max(now, accepted_at)` (and monotonic vs prior value) at all write sites, or tolerate inversion in Validate behind a diagnostic; add the clock-rewind regression test.

## Finding 2 — LOW severity / LOW likelihood / HIGH mechanical confidence: No upper bound on `run_control.workspace_quota_bytes`; int64 overflow silently inverts quota-pressure and retention gates

**Claim.** Config accepts any parseable int64 (config.go:393–398; only lower-bounded at config.go:498 and retention.go:29). For quota ≥ ~1.16×10¹⁷ bytes the expression `HardQuotaBytes*80/100` (sqlite.go:386, retention.go:109) overflows. Demonstrated wrap outputs: quota `1152921504606846976` → threshold **0**; quota `2000000000000000000` → threshold **−60206966633859645** (always-pressure).

**Bad outcome.** With a negative/zero wrapped threshold, `pressure` is permanently true: every `Accept` invokes `Compact(ctx,64)` with `compactCutoff = now` (retention.go:111–114), deleting progress/message/omission events from up to 64 finished runs per call regardless of the configured 7-day full-history window — silent destruction of replayable history, plus per-accept compaction latency. Simultaneously `softQuota = Hard−16MiB` stays astronomical, so the soft acceptance gate can never fire and the disk fills until raw `SQLITE_FULL`. A user setting an "effectively unlimited" quota gets the exact opposite of intent, with no error or diagnostic.
**Fix:** reject quotas above a sane ceiling in `normalizeRetentionPolicy`, or compute pressure overflow-safely (`usage >= HardQuota/5*4`).
