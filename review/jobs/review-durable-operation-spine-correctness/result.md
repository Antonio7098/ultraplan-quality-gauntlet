## Findings

### F1 — TUI reruns of identical operations are blocked until retention expiry (~37 days) — Severity: HIGH, Confidence: HIGH (probe-proven)
`tui/app.go:236-238` derives the accept digest as `sha256(CanonicalRequest + "\x00" + InputFingerprint)` — no nonce, session, or token. `AcceptOperation` maps an alias PK conflict to `Existing:true` (`durable_operations.go:106-112`; alias insert `runcontrol/sqlite.go:445-455`), and aliases are only removed by FK cascade when the run row is deleted — i.e., after `FullHistory+TombstoneHistory` = 7d+30d default (`retention.go:142-150`, `model.go:423-424`, schema `sqlite.go:306-314`; `expires_at` is never written; `Compact` never touches aliases; `ResolveOperationAlias` has no terminal filter).
Observable bad outcome (probe): accept → finish(failed) → re-accept the same request returns `Existing=true`, lifecycle `failed` — the TUI shows the static "matching durable operation already exists" card and cannot start. Since governed inputs for smoke/review/execute exclude their mutable artifacts (`operations.go:663-686`), fingerprints repeat verbatim between attempts, so routine smoke retries, review reruns, and auto-next executes are locked out of the TUI. The web adapter does not have this problem (`confirmationDedupKey` includes the one-time preparation token, `security.go:396-451`), QA ops self-unblock via hashed `.run-state.json`. Violates CURRENT-CONTRACT rerun parity (TRD L2079, L436) and sprint-32's retry-safe-per-short-lived-confirmation intent.
Regression test: accept→finish→accept same digest must yield a new run; fix = include a per-preparation nonce in the TUI digest (mirroring web).

### F2 — User cancellation of an inner runtime run is durably recorded as `persistence_degraded` — Severity: MEDIUM-HIGH, Confidence: HIGH (probe-proven)
The trailing coalesced-omission flush runs on the already-cancelled `runCtx` (`run_control.go:302-316`) instead of a detached bounded context; its failure unconditionally becomes `persistenceErr`, which skips `terminalOutcome` and proposes `TerminalPersistenceLost` (`run_control.go:322-331`; `Append` returns `ctx.Err()` at `sqlite.go:639-645`).
Probe: two identical tool-progress events 250ms-window-coalesced, parent cancelled → journal terminal `persistence_degraded` / "durable event persistence failed", returned error `persist progress omission: context canceled`. Routine Ctrl-C/deadline/durable-cancellation with pending omissions therefore pollutes the persistence-failure signal, misleads operators, and contradicts the outer tier which records `cancelled` for the same user action. Trigger is common (bursty tool-part updates within the 250ms window then cancellation).
Regression test: probe above must yield `TerminalCancelled`.

### F3 — Outer tier never records persistence loss mid-run; tick failures vanish silently — Severity: MEDIUM, Confidence: MEDIUM-HIGH
`ownedDurableOperation` has no persistence tracking (`durable_operations.go:21-32`): `RecordOperationEvent` append failure just calls `owned.cancel()` (:208-216), and every `controlOperation` tick failure cancels and exits without surfacing or persisting anything (:235-261). `FinishOperation`'s mapping (:286-297) has no persistence branch, so such runs terminalize as `cancelled`/`failed` — never `persistence_degraded` — in contrast to the inner tier in the same package (`run_control.go:196-203,322-331`). Concretely reachable under hard-quota pressure, where non-reserved progress appends fail while reserved terminal/warning writes still succeed (`sqlite.go:620,713-720`): journal says "operation cancelled", truth is "storage full". Also contradicts the surface invariant that persistence loss ends in a `persistence_lost` terminal.
Regression test: fault-injected Append after start must produce `TerminalPersistenceLost` (or at minimum a persisted warning); today it produces `cancelled`.

### F4 — Web/TUI operation cancellation bypasses durable cancellation recording — Severity: LOW-MEDIUM, Confidence: HIGH (code)
Hub cancel only fires the local context cancel (`web/operations.go:347-374`); same for TUI (`tui/app.go:256`, copy at :265 claims "durable cancellation"). No `RequestCancellation` row/event is written for hub-owned operations, so `cancellation_state` stays `none`, no ownerless cancellation/ack events exist, and cross-process observers see the run active until the abrupt finish. TRD requires cancellation be "idempotent, durably recorded … arbitrated". The durable path exists (`app/run_commands.go:216`; handler fallback `operation_handlers.go:206-213`) but is reached only when the hub record is absent.

### F5 — Hub mutex held across acceptance I/O stalls all operations — Severity: LOW-MEDIUM, Confidence: MEDIUM
`startConfirmed` holds `h.mu` across token consume + `AcceptOperation` — including claim and the first append with its ≤5s Busy/Unavailable retry loop (`web/operations.go:151-218`; `run_control.go:345-356`). A slow or contended database (multi-process same-workspace access is a supported TRD scenario; busy_timeout is 5s) freezes `status`, `subscribe`, SSE fan-out, and every other start for the whole process.

### F6 — Promoted display keys can never persist; every message event gains a misleading "unsafe" omission — Severity: LOW, Confidence: HIGH (code)
`runtimeEventDraft` promotes `text/delta/content/title/native_type/line` "that the run timeline JS expects" (`run_control.go:450-453,478,521-529`), but the storage allowlist omits exactly those keys (`sanitize.go:10-21,36-50`), dropping them and tagging each event `unsafe event detail omitted`. Assistant/tool text is thus never durable despite the pipeline's stated purpose, and omission counts inflate with non-unsafe content — an internal contradiction between the two layers of this surface.

## Defended / non-issues
- Empty CLI digest writes no alias (`sqlite.go:445`) — no CLI dedup, consistent with synchronous one-shot commands.
- Alias-conflict `Existing` results carry caller ctx without ownership — safe because no adapter executes on `Existing`.
- `payloadHash` concatenation cannot collide (unique sorted keys, `k=v\x00` framing); byte-truncation rune-splits are mirrored storage-side and JSON-safe.
- QA fence heartbeat after finish correctly fails `ErrStaleFence` (attempt outcome set, `lifecycle.go:38-55`); pre-finish `WithoutCancel` heartbeats work (test-pinned).
- `FinishOperation` flush failure corrupting outcome to `timed_out` needs a <5s finish context; all wired callers pass ≥30s — unreachable today.
- Cross-manager finish nil-op success is unreachable in wired topologies (one manager per serve/TUI session/CLI command).
- Trust boundary holds end-to-end: fingerprint stripped and recomputed server-side at prepare and again before execution (`operations.go:215,376-409`), token consumption binds session+canonical+fingerprint (`security.go:413-437`), digests derive only from server-side data.
