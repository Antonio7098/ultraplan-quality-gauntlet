# Findings: repo-publication security/misuse review

## F1 — Ambient `GIT_*` redirection variables leak into every publisher git invocation; a stray `GIT_DIR` makes publication build and push a synthetic commit of the wrong worktree into the wrong repository

**Claim.** `gitEnvironment` (internal/platform/gitpublish/publisher.go:284-302, applied at :269) deliberately constructs the child env but pins only `GIT_TERMINAL_PROMPT` and `LC_ALL` (plus `GIT_INDEX_FILE` per-call). Every other `GIT_*` variable — including `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_CONFIG_COUNT/KEY_n` — passes through from the ultraplan process environment into all ~12 git invocations in `Publish`/`commitPaths`.

**Observable bad outcome.** Verified experimentally with git 2.55: with `GIT_DIR=<repoB>/.git`, `git -C <repoA> rev-parse --show-toplevel` still reports `<repoA>` (cwd-derived), while `--git-dir`, ref reads, and object writes resolve to repoB. Walking `Publish` with a stray `GIT_DIR`: repo resolution (:79), path containment (:96, validated against the *reported* toplevel), branch resolution (:87), temp-index seeding from the foreign HEAD (:225), staging of *this* worktree's files (:228-231), `write-tree`/`commit-tree` into the *foreign* object DB (:232, :244), CAS `update-ref` moving the *foreign* branch (:253), and the bounded push (:154/:157) all execute against the foreign repository. Concretely:
- Execute stage (`All: true`, internal/sprint/publication.go:63): the entire dirty state of worktree A (including untracked, non-ignored files) is committed onto repo B's history and pushed to B's configured/upstream remote — externally visible, effectively irreversible.
- Workspace/planning stages: governed workspace documents (roadmaps, requirements, reasoning) get committed and pushed onto the implementation repo's remote — cross-repo exfiltration-shaped outcome, with the CAS silently succeeding because parent/branch both come from the same wrong repo.

**Trigger/preconditions.** `stage_completion != off` plus any inherited `GIT_DIR`/`GIT_WORK_TREE`/etc. Realistic sources: GitLab CI exports `GIT_DIR` in job scripts; running ultraplan from git hooks, `git rebase -x` exec lines, worktree helper wrappers, or sourced shell tooling. No attacker required; a misconfigured automation env suffices.

**Evidence / path.** publisher.go:75-166 (whole sequence), :268-273 (`exec.CommandContext(...); cmd.Env = gitEnvironment(extraEnv)`), :284-302 (override map lacks all `GIT_*` redirection vars). Repo-wide grep shows zero scrubbing of these variables anywhere in `internal/`; tests (publisher_test.go) never exercise a polluted env.

**Controls searched (counter-evidence).** Config validation covers mode/remote/timeout only (internal/platform/config/config.go:475-486); `-C` does not defeat `GIT_DIR` precedence for the database (demonstrated above); the publish lock lives under the possibly-redirected `--git-common-dir` (:100-112), so even locking follows the wrong repo. Nothing mitigates this.

**Severity / confidence.** Severity: Medium (wrong-repo commit+push of unrelated or private content; irreversible once pushed). Confidence: High on mechanism (reproduced), Medium on trigger prevalence.

**Regression test / fix proof.** In `publisher_test.go`: init two repos A/B; `t.Setenv("GIT_DIR", B/.git)`; `Publish(Request{Root: A, Paths:["owned.txt"], ...})`; assert either an explicit error or that B's refs/objects are byte-identical before/after. Fix: strip the `GIT_*` redirection namespace (or allowlist env) in `gitEnvironment`.
