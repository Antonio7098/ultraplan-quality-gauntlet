# Findings — `durable-operation-spine` (independent correctness review)

## F1 — Cancellation/timeout of inner runs is misrecorded as `persistence_degraded` when trailing coalesced omissions are pending
**Severity: High · Confidence: High (empirically reproduced)**

- **Claim:** `controlledRuntime.StartRun` flushes pending coalesced-progress omissions on the already-cancelled `runCtx` after `base.StartRun` returns (run_control.go:304-315). `Append` fails fast with `ctx.Err()` on a dead context (sqlite.go:639-644), which sets `persistenceErr`, and the function then takes the persistErr branch (run_control.go:322-331): it proposes `TerminalPersistenceLost` ("durable event persistence failed") and returns the persistence error — `terminalOutcome()` is never reached.
- **Bad outcome:** A plain user cancellation or parent-deadline expiry is permanently journaled as infrastructure failure (`persistence_degraded`), and the caller receives `persist progress omission: context canceled` instead of a clean cancellation. `persistence_degraded` sits in the uncertain/degraded class (model.go:103), driving wrong operator response and recovery guidance.
- **Trigger:** ≥2 identical progress events within the 250 ms window (same draft payload hash; hash excludes only runtime ids) still pending when the run ends by cancellation or deadline. The adapter pump (runtime.go:332-344) forwards provider part updates synchronously, so rapid identical status payloads are plausible during tool-execution polling.
- **Evidence:** Reproduced at the frozen commit: cancelled spy run emitting two identical `progress/tool {status:"running"}` events → `terminal=persistence_degraded reason="durable event persistence failed"`, `runErr=persist progress omission: context canceled`. Control run (one event, no pending omission) → `terminal=cancelled reason="runtime cancelled"`. The only difference is the flush context.
- **Counter-evidence checked:** Manager tier performs its equivalent flush on a fresh detached/bounded caller ctx (durable_operations.go:78-83, :274-282) — the asymmetry shows flushes were meant to survive cancellation. No test covers this path (pack §10 gap confirmed). Storage-side fencing is not the cause; the terminal proposal succeeds.
- **Regression test:** Cancelled run with pre-seeded coalesced omissions must yield `TerminalCancelled` and no persistence error (the repro test above, inverted assertion).
- **Fix direction:** Flush with a detached ≤30 s ctx (mirroring terminal proposals), or skip the flush and fall through to normal outcome mapping when `runCtx.Err() != nil && persistenceErr == nil`.

## F2 — Manager-tier control-loop failures kill operations silently and journal them as user cancellations
**Severity: Medium · Confidence: High (empirically reproduced)**

- **Claim:** In `controlOperation` (durable_operations.go:235-261), any error from `Snapshot`, `AcknowledgeCancellation`, `Heartbeat`, or `Reconcile` calls `owned.cancel()` and returns with **no retry, no log, no persisted warning event, and no persistence-loss classification**. These calls get zero retries while `Append` gets a 5 s retry loop.
- **Bad outcome:** A single transient SQLite failure past `busy_timeout` (5 s, sqlite.go:23 — plausible under the designed concurrency of 8 web operations plus inner runs each doing 1 s Snapshot polls and 10 s Reconciles against one file) aborts a long-running operation. Reproduced: one failing `Snapshot` poll silently cancels the context; the journal shows only `lifecycle=running` with no diagnostic, and after adapter finish the terminal reads `"cancelled" / "operation cancelled"` — a storage death recorded as user intent.
- **Contract:** Sprint 35 acceptance criteria require "event loss or persistence failure is never silent"; TRD §17 requires safe fail-closed behavior *with classification* for heartbeat/poll failures. The runtime tier does this correctly (`setPersistenceErr` → `persistence_degraded` + joined error, run_control.go:263-298); the manager tier does not.
- **Regression test:** Failing-repository wrapper around `Snapshot` → assert a warning event or `persistence_degraded` terminal, and that the surfaced result distinguishes storage failure from cancellation.

## F3 — Promoted observability keys are systematically dropped by the storage gate, stamping "unsafe event detail omitted" on benign events
**Severity: Low-Medium · Confidence: High (empirically reproduced)**

- **Claim:** `runtimeEventDraft` deliberately extracts/promotes `title`, `text`, `delta`, `content`, `native_type`, `line`, and `parent_child`-namespaced keys for the timeline (run_control.go:450-453, :477-485, :521-529 comments say "the run timeline JS expects payload.title…"); the platform adapter promotes the same fields upstream (runtime.go:675-687). The storage sanitizer's **allowlist** (sanitize.go:10-21) contains none of them, so every such field is dropped and each event records an omission.
- **Bad outcome:** Reproduced: an event whose app-layer payload contains `title/text/delta/detail/line/native_type/part{...}` persists only `detail/kind/status` (+identity); omission `Reason:"unsafe event detail omitted", Count:6` is written. The bounded, redacted fields the pipeline exists to surface never reach the journal; `omission_total` inflates; operators see "unsafe" omissions implying sanitization events that are actually schema mismatch. The promotion logic is dead code end-to-end.
- **Counter-evidence checked:** Raw-payload prohibition is intentional, but these values already passed bounding/redaction; `tool_arguments/tool_result/tool_status` etc. (allowlisted) do survive, proving selective intent rather than blanket policy. No test asserts end-to-end survival of these keys (existing tests stop at `runtimeEventDraft`), so nothing pins the current behavior as desired.
- **Regression test:** Append a draft with promoted keys; assert they survive (or, if policy is to drop them, delete the promotion code and stop recording them as unsafe omissions).

## F4 — Web/TUI cancellation of hub-owned operations bypasses durable cancellation recording
**Severity: Medium-Low · Confidence: High (behavior), Medium-High (contract breach)**

- **Claim:** `handleOperationCancel` first tries `hub.cancelOperation`, which for any operation this server owns merely fires the local context cancel (operations.go:347-374); the persisted path `runs.CancelRun` (→ `RequestCancellation`) is reached **only when the hub does not know the id** (operation_handlers.go:206-213, :381-396). TUI's 'c' key likewise cancels locally (tui/app.go:118-119). The only production writer of persisted cancellations for outer operation runs is the manual `ultraplan run cancel` CLI (run_commands.go:216).
- **Bad outcome:** For the primary cancel UX, the outer-run journal never receives a cancellation-request event nor a fenced acknowledgement; the control goroutine's `CancellationRequested`/ack branch (durable_operations.go:240-247) is unreachable from web/TUI. Cross-process observers never see `cancelling`; the run flips running→terminal-cancelled with no request facts.
- **Contract:** TRD §17: "Cancellation … **durably recorded**, routed through the canonical product/runtime cancellation path"; run details must include "cancellation request/acknowledgement facts". Sprint 35 requires authorized cancellation to resolve the durable run through the coordination mechanism.
- **Fix direction:** On hub cancel of a durable op, call `RequestCancellation(runID)` and let the existing ≤1 s observe→ack→cancel loop do its documented job (local cancel as fallback).

## F5 — Hub mutex held across acceptance storage I/O stalls the whole operations API
**Severity: Low · Confidence: High (mechanics)**

- **Claim:** `startConfirmed` holds `h.mu` across `manager.AcceptOperation` (operations.go:151-218), i.e., across Accept+Claim+first-append, each subject to 5 s busy timeouts plus the 5 s append retry. Under a DB stall every other operations request — status, cancel, SSE subscribe, start — blocks behind it for potentially ~15 s. Bounded but API-wide.

## Defended non-issues (counter-evidence found)

- **App denylist gaps** (`x-api-key` hyphen bypasses `api_key` marker): closed by the storage allowlist dropping unknown keys plus value-marker rejection of `sk-`/`bearer ` strings — verified both layers.
- **Alias-conflict `Existing` returning caller ctx:** all three adapters handle Existing without executing (TUI card, web doc without record/hub registration); dedup key embeds session, tokens are single-use and consume-bound to canonical+fingerprint — no cross-session hijack path.
- **Fingerprint TOCTOU:** consume() re-compares against a freshly prepared canonical+fingerprint at start time, and `RunOperation` re-verifies again after acceptance (operations.go:407-409), failing closed before child dispatch; a stale post-accept rejection burns only the alias row.
- **CLI empty-digest acceptance without PrepareOperation:** deliberate third regime; the fingerprint-confirmation contract is scoped to the browser dashboard section of the TRD, and acceptance itself still occurs.
- **Coalescing clock skew:** negative-elapsed guards in both tiers; conservative wall-clock basis only under-coalesces.
- **Metadata injection:** cloned before mutation (run_control.go:186-187); target extraction reads pre-stamp values.
- **Signal wiring:** `signal.NotifyContext` at cmd/ultraplan/main.go:19 feeds deps.ctx → accepted contexts drain to cancelled terminals correctly.
- **Finish pairing:** all 10 CLI sites pair begin/finish; inventory test pins counts; post-terminal stray events are rejected by storage fencing and harmlessly swallowed.
- **Web degrade mode** (`durable==nil`) is currently unreachable — serve always wires a manager (serve_commands.go:81).

The strongest issue is F1: the durability spine's system of record can permanently mislabel ordinary operator cancellations as infrastructure degradation, with the trigger inside the spine's own coalescing feature.
