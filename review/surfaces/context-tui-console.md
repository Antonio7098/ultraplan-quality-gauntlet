# Context Pack: `tui-console` — TUI console dashboard and operations

Target: ultraplan-go @ 8eef70f4903b25580719960009a170945bdad9ad (frozen).
Planning context: ultraplan-workspace @ ab12dc38059c9bf485f9aced9075bcd7d924cac5.
Domain: operator-interfaces. Risk: normal. Descriptive only — no defect judgments.

## 1. Purpose

Bubbletea terminal dashboard over the same typed app use cases as CLI/web. It navigates workspace/project/sprint/study/run state, previews artifacts, and launches the full sprint operation menu (status, validation, prompt, flow dry-run/run, execute, review, verify, smoke, QA) plus study run-loop operations through one mandatory confirm-then-accept pipeline for runtime-backed or mutating actions, with durable acceptance delegated to the run-control-backed `DurableOperationManager`. Foreground study runs can be detached with esc without cancelling; `c` requests durable cancellation; quit is refused while an operation is running in-process (doc.go:1-17; tui_commands.go:80-91).

## 2. Entrypoints and control flow

### 2.1 CLI wiring (`tui`, tui_commands.go:21-61)
`runTUI` admits no args except `--help/-h` (else ExitUsage); discovers workspace (ExitWorkspace on failure), loads effective config, builds `qaSettings` (ExitConfig), then composes `dashboardUseCases{root, stageRuntime, reviewConcurrency=DefaultParallel, smokeSettings, qaSettings}` plus `runs=repositoryRunUseCases` (run-control repository opened via `runRepository`, run_commands.go:42-61), `durable=newDurableOperationManager(repository, owner)`, and `runner=sharedOperationRunner(...)`. Missing `deps.tuiRunner` → ExitError "tui.start"; runner error wrapped the same class. main.go:19-29 supplies the signal-notified root context (`SIGINT/SIGTERM`) and wires `tui.Run`. `tui.Run` (internal/tui/app.go:23-33) requires UseCases, defaults Stdout to io.Discard, and starts a Bubbletea program with AltScreen writing to `deps.stdout`; initial geometry 100×40 until WindowSizeMsg (app.go:45-50).

### 2.2 Key dispatch (app.go:56-230)
Keys map through `KeyToAction` (keys.go:24-55): q/ctrl+c quit, esc/backspace back, tab focus, h/l/k/j+arrows, 1/p projects, 2/u studies, w runs, r refresh, c cancel, enter/o open. Precedence per KeyMsg:
- **Parallel form capture** (app.go:63-99): while `ParallelForm != nil` all keys are form-local — esc clears; backspace edits digits; enter parses parallelism (blank ⇒ 3, else 1..64 enforced locally) and issues `confirmationCmd`.
- **ActionConfirm** branch exists (app.go:102-106) but no key produces it today (`KeyToAction` never returns it); confirmation actually executes through **ActionOpen** precedence (app.go:153-192): existing Confirmation (if not Running) → beginOperation; RunView toggle previous; foreground study-run toggle previous; selected `ViewRun` opens the study run view (+refresh+1 Hz tick); selected Validation/Operation/Path issues validation/confirmation/preview commands (study start/resume operations open the ParallelForm instead, model.go:175-181); fallback delegates to inner model and re-polls when on a RouteRun.
- **ActionCancel** ladder (app.go:107-141): (1) Running ∧ ActiveRunID≠"" → `CancelRun(ActiveRunID, "user_requested")` via the RunUseCases capability; (2) Running ∧ local cancel func → cancel the operation context (lane used by non-durable runs); (3) current route is a run detail → `CancelRun(route.RunID)` and refresh (notice stored in the Error field, app.go:127); (4) study context (RunViewStudy or selected item's ViewRun) ∧ !Running → `beginOperation({Kind: OperationStudyCancel, Study})` directly; (5) no-op.
- **ActionQuit** (app.go:142-149): if Running, refuses to exit — hides the operation pane and sets the error banner "active durable work was not cancelled…". Otherwise delegates to the inner model (Quit flag) and returns `tea.Quit`.
- Back/left/right/tab delegate to the inner model except Back during a visible foreground study run, which detaches (`OperationHidden=true`) + refresh without cancelling (app.go:193-200).
Async messages: OperationMsg terminal (clears cancel/eventStream + refresh); OperationEventMsg appended while Running then re-arms `waitOperationEvent`; Load/Refresh/Preview/Validation/Confirmation messages update the inner model; `runViewTickMsg` reschedules itself every second while a study run view or any RouteRun is open (app.go:222-226, 271-273).

### 2.3 Operation lifecycle: confirm → accept → run → finish (app.go:232-322)
`beginOperation(req)`: derives a cancellable child of the root ctx; if use cases implement `DurableOperationManager` **and** a Confirmation is present, computes digest = sha256(CanonicalRequest + "\x00" + InputFingerprint) (app.go:235-238) and calls `AcceptOperation`. Accept failure surfaces as model Error; `Existing` alias hit renders a non-running result ("matching durable operation already exists") with the existing lifecycle/run ID (app.go:245-250). Otherwise the accepted run ID and its owned operation context are adopted; the model flips Running, clears events/confirmation/run view, records ActiveOperation/ActiveRunID, seeds a status line ("c requests durable cancellation; q keeps the run active"), creates a 128-buffer event channel, and batches `operationCmd` + `waitOperationEvent`. `operationCmd` (app.go:282-312): every emit first attempts `RecordOperationEvent(context.Background(), …)` — persistence errors drop the UI event silently, `committed==false` (coalesced) drops too, then a non-blocking channel send drops on full buffer; on return it stamps RunID, calls `FinishOperation` with a 30 s background timeout (error joined into the result), and emits OperationMsg.

### 2.4 Durable manager semantics (durable_operations.go)
`AcceptOperation` (97-138): Accept row (alias dedup only for non-empty digests, 106-112) → Claim with OwnerLeaseDuration → append lifecycle running event (failure proposes persistence_lost terminal, 121-129) → ownership value {repository, fence} stored in the operation context (130-131) → control goroutine started (136). Control loop (223-264) ticks at OwnerTickInterval: snapshot; requested cancellation ⇒ AcknowledgeCancellation + cancel; heartbeats each HeartbeatInterval; periodic Reconcile; any error cancels the operation. `RecordOperationEvent` (158-221): progress coalescing window keyed on stage/task/state/summary/tool fields with omission accounting merged into the next persisted record; payload keys whitelisted; append failure cancels the owned operation (213-215). `FinishOperation` (266-300): flushes trailing omission record, stops the control goroutine (<-done), maps outcome (deadline→timed_out; canceled/state-cancelled→cancelled; err→failed; partial→interrupted; else succeeded) and CAS-proposes the terminal.

### 2.5 Dashboard/refresh data path (app.go:343-400)
Every load/refresh/tick runs `dashboardAndRuns`: full `Dashboard(ctx)` projection (projects + studies + sprints; SprintSummaries calls per-sprint `Status` and `QAStatus`, sprint_usecases.go:363-470; StudySummaries loads/reconciles-in-memory/summarizes run state and probes lock liveness, study_usecases.go:74-157) → `Runs(limit 200)` (ErrWebUnavailable tolerated ⇒ zero page) → if the current route is a run detail, locate its snapshot and fetch `RunEvents(after = OldestRetainedSequence−1, limit 200)` (app.go:372-386). Preview uses `PreviewArtifact` (32 KiB cap, allowlisted basenames/dirs, symlink rejection, JSON validity flag; usecases.go:159-242). Refresh clears the preview pane; stale async results are dropped by exact-route comparison (model.go:190-217).

### 2.6 Inner model and rendering
Inner Model (model.go:56-85) holds tabs/routes stack/selection, panes (preview/validation/confirmation/operation/events), Running/ActiveOperation/ActiveRunID/ParallelForm, Runs page + deduped DurableEvents (≤200 by RunID:Sequence, model.go:342-357); operation event window capped at 100 (model.go:227-230). `navItems` (model.go:408-571) enumerates per-route menus: sprint route exposes artifact entries plus ~40 operations including flow dry-run/run per stage, execute start/resume, review start/restart, verify dry/start × review/smoke, smoke status/dry/start and a diagnostic-override variant carrying hard-coded rationale "operator requested guarded TUI diagnostic evidence" (model.go:498); QA routes expose status/dry/start/resume/recover, "View QA durable run" when `s.QA.RunID != ""`, shard-focused start/resume (Task=shard ID), theory drill-downs; study route shows View Run [ACTIVE] when lock-liveness says active, else one unified "Run Loop [RUNTIME]" (OperationStudyResume, Parallelism:3). Rendering order (views.go:15-58): header (title/tabs/breadcrumb/loading/error/background banner) then body priority ParallelForm > RunView > Confirmation > Operation(!hidden; foreground renderer for study kinds) > Validation > Preview > route summary + nav list, framed by a follow-selection viewport (or offset scroll for previews) and the help footer (keys.go:57-59). Specialized renderers: foreground run aggregates latest event per task with token/duration sums and active/previous split (views.go:72-132); study run view adds fallback-saturation (≥2 tasks), stale>2m banners, retries, attempt-history arrows (views.go:162-310); run-detail card renders lifecycle/liveness/product-status/cancellation/history retention/terminal plus retained events with omissions (views.go:319-349); QA views render only the bounded app projection with verdict-neutral wording ("Read-only QA completed", never "QA passed"; qa_view.go:8-45). Markdown previews render through glamour with word wrap and raw-content fallback (markdown.go:9-31). All output styled via lipgloss palette clamped to width (theme.go).

## 3. Inputs / outputs

Inputs: keystrokes and window size (sole interactive sources); workspace files read by Dashboard projections (project-index/roadmap/docs, sprint artifacts incl. flow-state.json/.run-state.json, study trees/run-state); effective config (stage runtimes, DefaultParallel, smoke/qa settings from env+yml); run-control DB pages/snapshots/events; wall clock (1 Hz tick, stale computations upstream). Untrusted content displayed: agent-derived OperationEvent messages/stats, OperationResult content/findings/error causes, artifact preview bytes, sanitized durable run events with omission metadata. Outputs: altscreen frames to stdout; durable rows/claims/events/terminals/cancellation requests in `.ultraplan/run-control.db` via capabilities; SIGINT to a foreign run-loop PID for study-cancel (locks.go:139-153); product mutations only through `RunOperation` → sharedOperationRunner/product services; process exit codes on startup failures (0/usage/config/workspace/error classes). The tui package writes no files of its own (doc.go:15-17).

## 4. Authoritative state

None owned here. In-memory only: Model fields and teaModel's ctx/cancel/eventStream (model.go:56-85; app.go:35-42). Durability lives elsewhere: run rows/events/terminals in run-control DB (spine surface), product artifacts/flow-state under workspace paths, QA verification tree. Dashboard reads are snapshots rebuilt on every load/refresh/tick; nothing cached across frames beyond the model copies. Note the composition keeps `readOnly=false` (tui_commands.go:41-46 does not set it), so per-sprint Status during refresh may rewrite deterministic flow-state.json status sub-records (usecases.go:130-132; disclosed in tuiHelp, tui_commands.go:88-90).

## 5. Invariants (as implemented)

- Accept-before-execute for every runtime/mutating operation that has passed PrepareOperation: AcceptOperation precedes RunOperation, alias digest derived from server-issued canonical+fingerprint (app.go:235-254).
- Stale-input guard: ExpectedFingerprint cleared at prepare, re-derived and compared inside RunOperation before execution (operations.go:215, 376-385).
- Quit refusal while Running; esc detaches foreground study runs without cancellation; `c` prefers durable cancellation request over local kills whenever a durable run identity exists (app.go:107-149).
- Presentation is best-effort downstream of durability: events reach the screen only after successful journal append and only if not coalesced and buffer not full (app.go:287-299).
- Bounded memory/UI: Events ≤100, DurableEvents ≤200 deduped, Runs ≤200, RunEvents ≤200/page, preview and operation content ≤32 KiB, task-error strings ≤300 chars (views.go:305,312-317).
- Single foreground operation at a time (Running gates confirm/open paths).
- Async results addressed to other routes are discarded (route equality guards, model.go:190-217).
- Local parallelism admission (blank⇒3, 1..64) mirrors server-side bound (app.go:76-85; operations.go:306-308).
- QA rendering consumes only bounded projections and never promotes QA completion to a verdict (qa_view.go comment/test-enforced).
- Navigation labels never leak artifact paths (views_test.go:10-48 enforces label-only rendering).

## 6. Trust boundaries

- Keystrokes construct OperationRequests locally; identifiers originate from dashboard projections and pass `validateOperationScope` ([A-Za-z0-9._-], ≤128 chars, no separators; operations.go:541-557) and QA-specific field restriction (project/sprint/map-owned shard only; operations.go:361-374).
- Local TTY assumed instead of transport controls: no session/origin/CSRF machinery; whatever shares the terminal can inject keys (doc.go framing).
- Confirmation authority stays server-side: CanonicalRequest/InputFingerprint are produced by PrepareOperation (operations.go:345-358); the adapter only hashes them into the alias digest; ExpectedFingerprint is stripped from caller-supplied requests before prepare (operations.go:128-133, 215).
- Agent/runtime-derived text reaches views after app-layer sanitization (`displaySafe` redaction + ANSI/control stripping, usecases.go:251-278; runtime summaries via runtimeProgressSummary) and journal sanitization upstream for durable events; TUI additionally truncates long task errors.
- study-cancel translates operator intent into a signal to another OS process identified solely by lock-file PID, refusing self-PID and cross-study locks (locks.go:141-153).
- Diagnostic override menu item embeds ForceReview + fixed rationale text in the constructed request (model.go:498).

## 7. External effects & lifecycle semantics

Effects per frame: none beyond stdout. Effects per action: run-control inserts/appends/terminal proposals/cancellation requests; product-stage mutations via services (flow/execute/review/smoke/QA writers, git publication inside those surfaces); SIGINT lane for study run-loops; possible flow-state.json status rewrite during Dashboard/refresh (§4). Cancellation lanes: (1) durable request → owner control goroutine acknowledges within tick cadence and cancels the operation context; (2) local context cancel for non-durable foreground work; (3) study SIGINT lane independent of run-control (shared-usecase-vocabulary seam). Detach (esc/q-refusal) never cancels; user-guide.md:376-391 states leaving/quitting the TUI leaves runs unchanged and points at `run list`/Runs view for recovery observation. Retry: none in-package beyond re-issuing an operation (alias dedup may return Existing for identical digests). Restart/recovery: repository open performs startup reconcile (run_commands.go:42-61); explicit recovery actions exposed as operations (QA Recover). Startup errors exit with classified codes before any program starts (usage/config/workspace/error); runtime failures land in OperationMsg → model Error + failed OperationError block with code/category/guidance mapping (operations.go:751-796).

## 11. Explicit unknowns / open questions (for later reviewers)

1. ActionConfirm is defined and handled but produced by no key binding; confirmation flows exclusively through ActionOpen's first precedence slot. Intent (reserved future binding vs leftover) is undocumented in-tree.
2. Study-cancel issued via the `c` ladder bypasses PrepareOperation/AcceptOperation entirely (constructed directly at app.go:139; beginOperation's durable branch requires Confirmation != nil), and because ActiveRunID stays empty, pressing `c` again takes the local-context lane rather than any durable lane. Whether this asymmetry vs other mutating ops is intended is unstated here.
3. UI event delivery is lossy by construction (persistence failure, coalescing, full 128-buffer all drop silently); the durable journal is the record. Operator-visible behavior when the journal is failing deserves reviewer attention.
4. `m.model.Error` doubles as a success-notice channel in the run-route cancel path ("durable cancellation requested", app.go:127); presentation-channel reuse is deliberate-looking but unpinned by tests.
5. When Runs listing reports ErrWebUnavailable, page is zero-value yet the code proceeds to render "Durable run is no longer retained." for any RouteRun detail (app.go:366-368; views.go:348) — wording may mislead when the store is merely unavailable vs pruned; untested either way.
6. PreviewMsg route guard treats zero Route as always-current (model.go:190-192) while Validation/Confirmation guards require exact equality — asymmetric staleness discipline between panes.
7. The 1 Hz poll continues while any RouteRun is open even if the run vanished from the page (tick condition app.go:222-226); polling lifetime depends solely on user navigation.
8. FinishOperation outcome mapping order makes OperationPartial reachable only when no error/cancelled state matched (durable_operations.go:286-297); which TUI paths can ever produce partial is undefined here (sharedOperationRunner returns complete/failed/cancelled only).
9. Width arrives fixed at 100 from the app layer (tui_commands.go:57) and height defaults to 40 until the first WindowSizeMsg; narrow-terminal behavior before resize is defined only by fullWidth clamping.
10. OperationMsg.Events exists in the DTO (model.go:118-123) but is never populated by operationCmd; terminal events must arrive via the stream before close.
11. POSIX assumptions inherited from dependencies (kill(pid,0) liveness, SIGINT lane, lipgloss/AltScreen terminal support) apply unconditionally; no build-tag variants exist in this package.
